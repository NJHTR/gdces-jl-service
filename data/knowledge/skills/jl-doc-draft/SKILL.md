# 出监理文书：先侦查，再落笔

你不是“收到字段就填表”的秀才。用户给的信息往往只有一句话、一张图。
**先去项目里找证据，再决定写什么、哪些字段有依据、哪些必须问。**

## 0. 先判断类型

能出草稿的类型只有：

- 监理通知单
- 监理日志
- 旁站记录
- 平行检查记录
- 监理检查记录

**巡视记录不是单份草稿**：它是按天汇总的省统表导出（docx），要引导用户去「资料/记录 → 巡视记录 → 生成这几天」。不要用 `create_doc_draft` 生成「巡视记录」。

## 1. 侦查（至少 3 个来源，别搜一次就收手）

按任务需要选，不要求每次都全做，但不能“什么都没看就写”：

```bash
jl-tool get_context '{"projectId":"<项目>"}'
jl-tool search_records '{"projectId":"<项目>","keyword":"<部位/问题>"}'
jl-tool search_photos '{"projectId":"<项目>","keyword":"<部位>"}'
jl-tool recall_memory '{"projectId":"<项目>","userId":"<用户>","q":"<关键词>"}'
jl-tool search_standards '{"query":"<规范关键词，可换同义词>"}'
```

工作区里可以直接读/搜（只读，别手写 md 当出稿）：

```bash
cat records/rules.md            # 项目约定：这个项目文书怎么写、怎么签
cat records/photos.md           # 影像索引：哪个部位拍过什么
ls docs/2026-*/                 # 近期同类文书
rg -n "<部位|问题|工序>" docs/ records/ knowledge/ 2>/dev/null | head -50
cat AGENTS.md                   # 项目事实与指针
```

侦查纪律：

- 规范全文不在工作区，**规范只能走 `search_standards`**；搜不到就换同义词/换关键词再试一次，仍没有就明确说“没查到依据”，不许拿相近条文凑数。
- 项目规矩、影像索引、历史文书、知识模板在**工作区/知识库**里，能 `cat`/`rg` 就自己找，不要等别人喂。
- 历史同类文书是最好的模板：找一份结构完整的，照着字段/语气写。
- 照片可以由你**自己判断选择**，不必等用户逐张点名：
  - 先用 `search_photos` 按部位、日期、施工内容、关键词找候选；
  - 按“同一部位 > 同一时段 > 同一问题/工序 > 用户本轮上传”排序；
  - 只选真正相关的，通常 1~3 张，最多 5 张；
  - 每张在 `bases` 的 `text` 里写清“为什么选它”（部位/时间/内容），并把 sha 写进 `ref`；
  - 不确定是否相关时，列出候选问用户“这两张用哪张”，不要全量塞当天照片。
- 用户明确点名某张/某个部位时，以用户点名为准，不要自作主张换图。
- 证据互相矛盾时停下来问，不要自己选一个。

## 2. 信息不足

先判断缺的是不是**关键信息**：

- 部位、事由、问题、时间、处理意见 —— 缺了会影响文书成立，**先问一句**，不要空着硬出；
- 非关键字段可以留 `待补`，但整份文书不能是空的。

底线：`fields` 全空、`obj` 也空时，**不允许调用 `create_doc_draft`**（后端会拒绝）。如果用户催着先出，至少用已掌握的一个事实立住 `obj`/一个字段，其余标 `待补`。

## 3. 落笔

```bash
jl-tool create_doc_draft '{"projectId":"<项目>","kind":"监理通知单","obj":"4#楼东侧外架","fields":{"部位":"4#楼东侧外架","问题":"连墙件缺失"},"bases":[{"kind":"rule","ref":"JGJ 130-2011#6.4.1","text":"..."}]}'
```

- `bases` 只放 `search_standards` 真实返回的条号；
- 字段里的每个事实最好能在侦查结果里找到出处；
- `create_doc_draft` 会写文件、提交、入库；**用 shell 手写 md 不算出稿**。

## 4. 自检

```bash
jl-tool validate_doc '{"kind":"<类型>","fields":{...}}'
```

告诉用户：出了哪份、编号、哪些字段是待补、依据是查到的还是没查到。

## 5. 用户说“记住 / 以后都这样 / 这个项目的规矩”

不要只回“好的，我记住了”——那样不会写进任何地方。

用项目规矩提案：

```bash
jl-tool propose_rule '{"projectId":"<项目>","text":"<一句话规矩>","source":"agent","evidence":"<用户原话或某份文书的修改>"}'
```

- 提案会进入「项目规矩 · 待确认」，用户采纳后才写进 `records/rules.md`；
- 以后每份文书出稿前都要先读 `records/rules.md`，按项目规矩写；
- 不要把一次性的现场事实写成规矩，只写会反复适用的约定。
