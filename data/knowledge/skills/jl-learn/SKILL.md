# 把一次纠正变成项目规矩

## 先判断：这是不是“规矩”

- **一次性现场事实**（今天几点、哪面墙、哪个人）→ 只改当前文书，不写规矩。
- **会反复适用的约定**（这个项目外架验收必须写步距跨距、日志不许编实测值）→ 候选规矩。
- 用户没明说“以后/每次都” → 先问一句：
  “这条要不要记成这个项目的规矩？以后同类文书都按它写。”

## 先查重，别重复造规矩

```bash
cat records/rules.md
jl-tool recall_memory '{"projectId":"<项目>","userId":"<用户>","q":"<关键词>"}'
```

已有相同/相近的规矩就不要重复提案；可以指出“已经有这条”。

## 提交提案，不直接写文件

```bash
jl-tool propose_rule '{"projectId":"<项目>","text":"<一句话、可执行、可验证的规矩>","source":"agent","evidence":"<用户原话或修改前后>"}'
```

- `text` 要具体到能检查，例如：
  - ✅ “监理日志的当日施工进展必须写清楼层和工序；不知道就标待补，不许编。”
  - ❌ “日志要写好一点。”
- `evidence` 放用户原话，或“字段 X 从 A 改成 B”。
- 提案只进入「项目规矩 · 待确认」，**用户采纳后才写进 `records/rules.md`**。

## 绝对不要

- 不要只回“好的，我记住了”——那句话不落任何地方；
- 不要自己改 `records/rules.md`（那是渲染视图，手改会被覆盖）；
- 不要把一次性的现场数据写成长期规矩；
- 不要在用户没确认时声称“已经生效”。

## 采纳之后

- 规矩进入 `records/rules.md`；
- 下一份文书出稿前必须读它；
- 如果新规矩和旧规矩冲突，先停下来问用户，不要自己选一个。
