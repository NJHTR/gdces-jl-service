# 表式文书：怎么保证格式（定稿）

> 针对「巡视记录等省统表明细：格式必须和原件一致、表式几乎不变、要多份」这个问题。
> 结论：**不手绘表格，用原件模板原位填字。**

---

## 一、先把问题定位清楚（都有证据）

你的疑问是「模板不是入库了吗？是不是没读到？」。查完是三层原因叠加：

```
① 入库了 —— data/knowledge/kb/templates/16巡视记录.md 确实存在
② 但被"压平"了 —— import-materials.py 的 docx_to_md() 把每行表格转成 | a | b |，
   还做了同行去重（第 52-58 行 uniq/seen）
   → 合并单元格、列宽、边框、行高全部丢失，只剩一堆字
③ 原件没留 —— 服务端 find data/knowledge -name '*.docx' 为空
   → 没有任何"可填的模板"，只有一段不像表的文字
```

于是模型即使读了这段 md，也不可能还原出「4 行 × 4 列、合并、□1..□4 清单」的版式；
而我上一版是**在代码里手绘了一张 5 行表**——那是二次创作，格式必然不一样。

**结论：问题不在"有没有资料"，在"资料里没有表结构"和"生成方式是手绘而不是套模板"。**

---

## 二、决策：模板填充（template-fill），不是让模型画表

既然表式几乎不变，就把**官方 docx 原件当成唯一规范**：

```
原件（人维护，git 版本化）  →  字段映射（JSON，声明哪个格子填什么）  →  填充器（代码，只写一次）
                                                              →  校验器（结构签名，不通过不交付）
```

模型只产出**结构化数据**（部位、时间、问题、处理、签字人），不参与排版。
排版由模板保证；内容由数据填。这就是"格式不会漂"的根本原因。

### 可行性已经实测（不是推测）

在 `16巡视记录.docx` 上原位填了「部位 / 时间 / 问题及处理」三个单元格，存盘后重新打开比对：

```
表格数 before/after：1 / 1
行列与合并结构一致：True
固定标签仍在：巡视的工程部位 ✓  施工单位 ✓  巡视时间 ✓  巡视内容 ✓  注：本一式一份 ✓
变化的单元格数：3（正好是填的三个）
```

也就是说：**填字不动结构**，格式天然等于原件。

## 三、三层结构（一次建好，后面加表零代码）

### 1. 模板层（数据）

```
data/knowledge/templates/docx/16巡视记录.docx      ← 原件，人放进来
data/knowledge/templates/docx/16巡视记录.fields.json ← 字段映射（声明式）
```

`fields.json` 示例（标签定位，不写死行列号，模板微调也不容易错）：

```json
{
  "form": "巡视记录",
  "code": "GD-B-214",
  "template": "16巡视记录.docx",
  "version": 1,
  "slots": [
    {"key": "project",  "label": "工程项目名称：", "target": "right", "kind": "text"},
    {"key": "parts",    "label": "巡视的工程部位", "target": "right", "kind": "text"},
    {"key": "org",      "label": "施工单位",       "target": "right", "kind": "text"},
    {"key": "period",   "label": "巡视时间",       "target": "right", "kind": "text"},
    {"key": "issues",   "label": "巡视发现的问题及处理情况", "target": "cell", "kind": "lines"},
    {"key": "inspector","label": "巡视监理人员（签名）：", "target": "inline", "kind": "text"}
  ],
  "fixed_labels": ["巡视的工程部位", "施工单位", "巡视时间", "巡视内容", "注：本表一式一份"]
}
```

**这是配置，不是硬编码**：加一张新表 = 放一个 docx + 写一个 fields.json，不改代码。
`fixed_labels` 同时是校验用的"必须还在"的清单。

### 2. 填充器（代码，只写一次）

`bffpkg/formfill.py`：

```
load(template) → locate(slot) → write(只改 run.text，保留字体/字号) → validate(signature) → save
```

要点：

```
· 只改目标单元格的 run.text，不重建段落（重建会丢样式）
· 合并单元格用"锚点单元格"写一次，避免重复写
· lines 类型按行拆段，段样式复制原单元格首段
· 多份记录：同一文档里复制模板的 table XML + 分页符（或每份一个 page section）
```

### 3. 校验器（保证"没走样"）

生成前后各算一次**结构签名**：

```
签名 = 表格数 + 每表(行数, 列数, 每行合并组数) + 固定标签集合 + 抽样字体字号
规则：
  · 生成后签名必须与模板一致，否则**不交付**（报错，而不是静默出一份不像的）
  · 只允许 slots 白名单里的单元格文本变化（diff 其它单元格必须为空）
  · 标签定位失败 → 直接报"模板与 fields.json 不匹配，请重新标注"
```

这条是**硬约束**：宁可生成失败并提示，也不能交出一份格式不对的文书。

## 四、多份表怎么出

```
一次导出 N 条记录 → N 份模板副本，按顺序排在同一个文档里，每份之间分页
编号：GD-B-214 + 顺序号（或项目编号+日期+序号）
页眉/页脚随模板走，不需要重建
```

不拼"一张大表"，因为省统表是**一张表一次巡视**，多张才合规。

## 五、要不要上 docxtpl（Jinja 模板）？

| 方案 | 优点 | 代价 | 适用 |
|---|---|---|---|
**python-docx 原位填字**（选它） | 不改原件；固定表式最稳；零新依赖（已装） | 只能"填格子"，做不了循环区块 | 省统表这种固定表 |
docxtpl | 支持循环/条件，批量强 | 要把模板改成 `{{ }}` 版（等于改原件或维护派生版） | 将来要"一张表内循环多行"时 |

**决定**：先用原位填字。等出现"一个表里要循环 N 行明细"的表式（比如材料台账），再引 docxtpl；
那时只换渲染器，模板与 fields.json 的规范不变，不会推倒重来。

## 六、与知识库的关系（避免两套真相）

```
交付以 docx 原件为准（格式）
md 转换件只做"检索摘要"（内容），并在文件头注明"结构以 docx 为准，勿据此还原排版"
导入时同时保留原件到 templates/docx/，不再只留 md
```

这修掉了现在这个坑：只留 md → 结构丢失 → 谁都无法还原。

---

## 七、落地顺序（半天到一天，之后加表零代码）

```
1. 模板入库：把 16巡视记录.docx 等原件放到 templates/docx/，写完 fields.json（巡视记录先做）
2. formfill.py：load/locate/write/validate/save（含多份复制）
3. /api/v1/reports/patrol 改成：取数据 → 填模板 → 校验 → 下发
4. smoke 加断言：生成后签名与模板一致、固定标签齐全、变化单元格 ⊆ 白名单
5. 其余表式（旁站/平行检查/监理日志/通知单/检查记录）按同一流程接入
```

## 八、验收清单

```
· 生成物与原件"同表数、同行列、同合并"——签名比对通过
· 固定标签（巡视的工程部位/施工单位/巡视时间/巡视内容/注）一个不少
· 只改了 slots 指定的单元格
· 多天 → 多张表，各自分页，编号连续
· 模板被改动且与 fields.json 不符时，导入期就报错（不等到出稿才发现）
```

## 九、明确不做

```
✗ 在代码里手绘省统表（已证明会漂）
✗ 让模型直接输出 docx/OOXML（格式不可控）
✗ 只用 md 充当模板（结构已丢）
✗ 把行列号写死在代码里（模板微调就崩；用标签定位）
✗ 校验失败还照常交付
```
