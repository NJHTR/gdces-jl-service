# 知识与记忆架构

> 这份文档回答一个问题：**多个用户、多个项目、多种模态的知识，放哪、怎么隔离、怎么长大。**
> 结论先行：**能用引擎的，就不自己造**。

---

## 一、四层 scope

不要把"隔离"理解成两层（用户/项目）。实际是四层，第四层最容易被漏掉：

| 层 | 内容 | 谁共享 | 生命周期 |
|---|---|---|---|
**组织知识** | 规范条文、法规、公司模板、技能包 | 所有人 | 长期、只读、版本化 |
**项目知识** | 现场记录、文书、图纸、项目约定 | 该项目所有人 | 项目存续期 |
**个人知识** | 偏好、习惯、被纠正过的事 | 跨项目跟随这个人 | 长期 |
**会话状态** | 这一轮聊到哪、正在做什么 | 某人 × 某项目 | 短（可压缩、可丢） |

**会话不是知识**。混在一起就会出现"把聊天记录当知识沉淀"。

## 二、落盘布局

```
data/
├── knowledge/                        ← 组织知识（只读、git 版本化）
│   ├── standards/                    规范条文（接 search_standards）
│   ├── templates/                    文书模板
│   ├── legal/                        法规
│   └── skills/<name>/SKILL.md        技能包（按需读）
│
├── homes/<user>/                     ← 个人知识（引擎家目录，每用户一个）
│   ├── config.toml                   指向百炼的配置
│   ├── memories/                     引擎自己的记忆（MEMORY.md / summaries）
│   ├── sessions/                     该用户的会话
│   └── skills/                       该用户私有的技能
│
└── workspaces/<project>/             ← 项目知识（共享、git 版本化）
    ├── AGENTS.md                     只放项目事实
    ├── docs/ records/ photos/
    └── .users/<user>/notes.md        个人在本项目的备忘（可选）
```

## 三、核心决定：用 `EASYCODE_HOME` 做用户隔离，不自研记忆系统

### 依据（源码）

```rust
// core/src/config/mod.rs:992
/// Directory containing all easyCode state (defaults to `~/.easycode` but can be
/// overridden by the `EASYCODE_HOME` environment variable).

// memories/read/src/lib.rs:13
pub fn memory_root(easycode_home: &AbsolutePathBuf) -> AbsolutePathBuf {
    easycode_home.join("memories")
}
```

**记忆根目录 = `$EASYCODE_HOME/memories`。** 所以：

```
每个用户启动 app-server 时传 EASYCODE_HOME=data/homes/<user>
→ 记忆、会话、技能天然隔离，不用写一行隔离代码
```

### 项目隔离怎么办？

引擎的记忆是"一个人一份"，不分项目。但它给出的 `MEMORY.md` 格式**自带项目边界**：

```markdown
# Task Group: <任务族>
scope: <这块覆盖什么>
applies_to: cwd=<工作目录>; reuse_rule=<什么情况可复用>
```

`applies_to: cwd=...` 就是项目边界 —— 这是引擎的整理提示词（`consolidation.md`）强制要求的字段。
**所以项目隔离靠"整理时的格式约束"，不靠目录切分。**

### 为什么不自己写一套

- 引擎已经实现了：从 rollout 抽取 → 合并 → 写成 `MEMORY.md` + `memory_summary.md` + `rollout_summaries/`
- 它的整理提示词有 880 行，涵盖去重、冲突处理、边界、脱敏
- 自己写一套 = 重复造轮子，而且必然更差

**我们要做的只有三件事**：
1. 给每个用户一个家目录（配置 + 权限）
2. 把项目事实写进 `AGENTS.md`（喂给它，而不是塞进提示词）
3. 在 workspace 里放 `data/knowledge/` 作为只读知识源

## 四、三种知识形态

| 形态 | 例子 | 存法 | 检索 |
|---|---|---|---|
**文本** | 规范条文、项目约定 | 文件（knowledge/ 或 AGENTS.md） | grep / search_standards |
**指针** | 照片、录音、图纸 | blob + **agent 写的描述** | 搜描述，命中后打开原文件 |
**经验** | "这个项目要求附对比图" | 引擎记忆（MEMORY.md） | memory_summary + grep |

**多模态的关键**：图片本身不进知识库，**图片 + 它的文字描述**进。
描述由 agent 写（它看得懂水印："沙盛四路 ss-w44，污水管道 沟槽开挖，10-27 晴 26℃"）。
这样"照片读完就没了"的问题才算解决。

## 五、冷启动 vs 慢慢长大

| | 冷启动 | 慢慢长大 |
|---|---|---|
**谁写** | 人（我们预先放） | agent（每轮/每次会话） |
**放哪** | `data/knowledge/` | `data/homes/<user>/memories/` |
**形态** | 只读、git 版本化 | 引擎自动整理 |
**例子** | 规范、模板、常用条文摘编 | "这个项目要附对比图""结论别写太长" |

两者**不混**：组织知识是"宪法"，个人记忆是"经验"。经验不能改宪法，宪法也不进个人记忆。

## 六、提示词的边界（回应"内置提示词太多"）

`AGENTS.md` 里**只允许三类内容**：

1. 项目事实（名称、编号、参建单位、部位命名习惯）
2. 项目约定（这个项目特有的规矩，不是通用做法）
3. 指针（"模板在 data/knowledge/templates/，需要时自己读"）

**不允许**：
- 工具清单（加了新工具就得改这里 → 必然漂）
- 说话风格、输出格式（这些交给 skill 或模型自己判断）
- 任何"如果用户说 X 就做 Y"的规则

判断标准一句话：**这句话会不会因为加了工具/换了模型而失效？会 → 别写。**

## 七、现在的问题与修法

| 现状 | 问题 | 修法 |
|---|---|---|
`AGENTS.md` 2778 字节，混了工具清单和说话方式 | 硬编码、加工具要改代码 | 瘦身到只留事实，行为移到 skills |
引擎记忆根全局（`~/.easycode/memories`） | 未启用是运气 | 用 `EASYCODE_HOME` 每用户一个 |
个人知识只能进 MySQL | 检索靠字面相似 | 迁到引擎记忆（文件 + 整理） |
知识没有冷启动包 | 每次现查规范 | `data/knowledge/` |
照片读完就丢 | 信息不沉淀 | 入库时 agent 写描述 |

## 八、验收（怎么知道做对了）

1. **隔离**：用户 A 说"记住：结论写短一点"，用户 B 问"我有什么要求" → B 答不出（不串）
2. **项目边界**：A 项目说"要附对比图"，切到 B 项目问"要附吗" → 不该照搬
3. **长大**：连说三次不同说法的同一条规矩 → 记忆里只有一块
4. **冷启动**：问"通知单模板长什么样" → 它去读 `knowledge/templates/`，不是凭空编
5. **多模态**：问"上周这个部位查过什么" → 凭照片描述能找回来
6. **提示词**：`AGENTS.md` ≤ 800 字节，且不含工具清单
