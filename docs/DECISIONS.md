# 决策记录

> 每个「当时为什么这么选」都记一条。不是为了留念，是为了**将来有人想改的时候知道代价**。
> 格式：背景 → 决定 → 代价 → 什么情况下该推翻。

---

## D1 · Agent 用 Python，业务未来用 Java

**背景**：一开始整个服务是一个 Python 文件，业务和调度缠在一起。

**决定**：按「变更频率」和「事务需求」切，而不是按技术层切。

| 层 | 语言 | 理由 |
|---|---|---|
Agent 运行时（任务编排、子进程、工作区 git） | Python | 跟进程和文件打交道，迭代快 |
业务域（文书状态机、权限、审计、报表） | Java | 事务、类型、MyBatis 写复杂查询；将来接签章/PDF/国密 |

**代价**：两个服务、两套部署、跨服务一致性要自己保证。

**什么情况推翻**：如果 Java 侧长期没人维护 —— 那时候两套比一套更糟，应该合回 Python。

---

## D2 · 不重写，用绞杀者模式一步步搬

**背景**：曾考虑把 2900 行 Python 整体重写成 Spring Boot。

**决定**：不重写。先定契约 → 再拆包 → 再一个域一个域搬到 Java，Python 通过 HTTP 调。

**代价**：短期两套代码并存，要维护 `BIZ_BASE_URL` 开关。

**什么情况推翻**：如果发现某个域在两边都要改（比如文书的校验规则），说明边界切错了，要重新划。

---

## D3 · doc 表只有一个写者

**背景**：容器里的 `create_doc_draft` 直接 `INSERT INTO doc`，BFF 的 `PATCH` 也写。并发会打架。

**决定**：工具只负责「写文件 + git 提交」，数据库那一行通过 `POST /api/v1/docs/register` 交给 biz。

**代价**：工具多一次 HTTP 调用（约 20ms）；容器必须能访问 BFF（改用 host 网络）。

**什么情况推翻**：如果以后 Agent 要离线工作（断网跑），就不能依赖在线接口 —— 那时需要本地队列 + 补登。

---

## D4 · 工作区文件由 Agent 写，数据库才是真值

**决定**：`.md` 文件和 git 提交由 Agent 侧负责；数据库是唯一真值。
需要时可以「从数据库重新渲染整个仓库」。

**代价**：文件和数据库可能短暂不一致（先写文件后登记）。

**什么情况推翻**：如果发现有人直接改仓库里的 md 而不改数据库 —— 那就得加反向同步或禁止手改。

---

## D5 · 前端在 Skyline 下只允许改「颜色和字重」做行内标注

**背景**：连续踩了两个坑：

1. `<view>` 下的多个 `<text>` 在 Skyline 里是**块级**，每个片段各占一行，样式直接崩
2. `class="seg"` 撞上了已有的分段控件样式（自带灰底圆角），文字像被选中
3. `scroll-view` 不给显式高度就**塌成 0**，Shell 面板空白

**决定**：

- 行内片段必须塞进**同一个 `<text>` 父节点**（嵌套 text 才走行内流）
- 行内标注只改 `color` / `font-weight`，**不碰 background / border / padding / line-height**
- 类名加前缀（`rt-`、`tl-`），避免撞车
- 需要滚动的地方先考虑普通 `view` + 限高裁切，`scroll-view` 只在必须时用且给死高度

**代价**：行内标注不能点击（嵌套 text 的事件在 Skyline 不可靠），依据要点得走下方脚注。

**什么情况推翻**：如果升级到支持行内富文本的方案（或改用 web-view），可以放开。

---

## D6 · 回复由后端清洗，不指望模型守规矩

**背景**：模型会把绝对路径、URL 编码、markdown 链接、提交号全吐进正文。

**决定**：两层治理 —— 提示词要求 + `clean_reply()` 硬清洗（剥链接、删路径、删编码串、
去「我先…」过程叙述、相似句去重、160 字封顶）。

**代价**：偶尔会误删（比如正常内容里的长数字串）。

**什么情况推翻**：如果换了输出更听话的模型，清洗层可以简化，但**不要直接删掉**。

---

## D7 · 结构化回答从数据来，不从模型的话来

**背景**：让模型按「结论/依据/待补」三行回答，两次都没照做。

**决定**：结论 = 这一轮生成了哪份文书（`doc.kind/obj`）；依据 = `cites`（工具真实输出解析）；
待补 = 文书 `fields` 里值为空的键。模型原话只作为「补充」放在最后。

**代价**：如果模型写了一堆有用信息但没建文书，这些信息只能作为补充段落，不做成结构。

**什么情况推翻**：如果模型能稳定输出结构化 JSON，可以改回让它生成，但**校验仍以后端数据为准**。

---

## D8 · 每用户串行，不用全局并发上限糊过去

**背景**：原来只有全局信号量（3 个并发），同一个人连发 3 条会同时开 3 个 turn，抢同一个工作区。

**决定**：`(项目, 用户)` 一把锁，先排自己的队再抢全局槽。

**代价**：单用户在长任务里无法并行。

**什么情况推翻**：上多进程/多机时，这把锁必须换成 Redis 分布式锁 —— 否则等于没有。

---

## D9 · 工具容器不用 stdin，改用临时文件

**背景**：`docker run -i` 在 code-mode 沙箱里拿不到 stdin 的 EOF，容器里 node 一直等输入，
任务卡 4 分钟；工具调用耗时从 0.6 秒到"挂死"。

**决定**：请求写临时文件 → 挂进容器 → 重定向喂给 server.js；另外加 60 秒硬超时。

**代价**：每次调用多一次文件 IO（可忽略）。

**什么情况推翻**：如果以后不用沙箱执行命令，可以回到 stdin。

---

## D10 · 主线路从中转切到阿里云百炼（qwen3.7-plus）

**背景**：`llmapi.xfcxb.com` 中转额度归零（`403 剩余额度 $0.000000`），
所有 AI 任务停摆。在服务器上另一个项目 `rokid_glass` 里发现一套可用的
阿里云百炼凭据（token-plan 套餐）。

**决定**：把引擎主线路切到百炼，`wire_api` 从 `responses` 改成 `chat`。

```toml
model_provider = "dashscope"
model = "qwen3.7-plus"
model_context_window = 131072
model_max_output_tokens = 16384

[model_providers.dashscope]
base_url = "https://token-plan.cn-beijing.maas.aliyuncs.com/compatible-mode/v1"
wire_api = "chat"
env_key = "DASHSCOPE_API_KEY"
```

原 `xfcxb` provider 段保留，随时可切回。

**代价**：

- 百炼是 Chat Completions 协议，和 Responses 的 reasoning 呈现方式不同
- 凭据属于另一个项目，**配额共享**，跑重任务会挤占对方
- 模型元数据 easyCode 不认识，要靠 `model_context_window` 手动补，否则走 fallback

**实测**（都在真机上跑）：

| 项 | 结果 |
|---|---|
简单调用 | `"引擎可用"` ✓ |
工具调用 | 调了 2 次 `jl-tool search_standards`，正确引用 JGJ 130-2011 第 6.4.3 条 ✓ |
端到端任务 | 36.1 秒 / 49.8 秒两轮，产物与引用都正确 ✓ |

**什么情况推翻**：如果 qwen 在多步工具调用上出现明显退化（比如漏调工具、
乱编条号），或者对方项目要用这套凭据，就切回中转或换 `deepseek-v4.1-flash`。

## D11 · 语音与视觉不自建，直接用现有能力

**背景**：之前讨论语音转文字要在「微信同声传译插件 / 云 ASR / 本机 whisper」里选，
看图也打算自己写 VLM 调用。

**决定**：全部不自建。

| 能力 | 用什么 | 为什么 |
|---|---|---|
语音转文字 | 阿里云百炼 `qwen-audio-3.0-asr-flash` | 已验证 `"欢迎使用阿里云。"` 识别正确，同一个 key |
通用看图 | `qwen3.8-flash`（OpenAI 兼容的多模态消息） | 已验证能正确描述图片 |
工地隐患识别 | 华工 `hazard_vlm_detection` | 专门的施工现场隐患模型，返回结构化风险判定 |
截图/看细节 | easyCode 原生 `view_image`（`detail: high/original`） | 框架已内置，不用自己写 |

**代价**：

- ASR 只吃 16k 单声道 wav，webm/mp3 要先转（容器里有 ffmpeg）
- 华工 VLM 要求文件带扩展名；我们的 blob 是纯 sha256 名，得先按内容改名
- 静音音频会返回 `400` + 空体 `{}`，不能当成服务故障
- 语音与视觉的能力都在**同一个百炼 key** 下，和 LLM 共享配额

**什么情况推翻**：如果要离线部署（工地没网），这些云能力全部不可用，
那时才需要考虑本机 whisper + 本地 VLM。

## D12 · wire_api 必须是 responses，不能用 chat

**背景**：为了换线路把 `wire_api` 从 `responses` 改成了 `chat`（百炼兼容模式）。
结果多 agent 工具全部 `unsupported call`，MCP 工具也调不通。

**决定**：**任何有命名空间的工具，都要求 `wire_api = "responses"`。**

**证据**：

```
chat 协议：    tool_name="spawn_agent" tool_namespace="functions"   → unsupported call
responses 协议：tool_name="spawn_agent" tool_namespace="collaboration" → 派发成功
```

chat 协议把工具调用统一落到 `DEFAULT_FUNCTION_NAMESPACE = "functions"`，
而多 agent 注册在 `collaboration`、MCP 注册在各自的 server 命名空间，
注册表按「命名空间 + 名字」精确匹配 → 查不到。
`functions` 是保留命名空间，改 `tool_namespace` 也进不去。

**代价**：chat 协议的模型（很多国产模型只提供 chat 兼容模式）只能用到
默认命名空间的内置工具（`exec_command`、`apply_patch`、`view_image` 等），
**用不了多 agent 和 MCP**。

**什么情况推翻**：如果 easyCode 后续在 chat 适配层做了「扁平化再还原」的映射，
这个限制就没了。到时候要重新测一遍，别照抄这条结论。

## D13 · 文书字段的规则放 schema，不放代码

**背景**：模型会把「待补」写成字段值，导致不齐的文书被当成可签。
第一反应是在后端加个 `if v in ("待补","待定")`，或者在详情页用正则认这两个字。

**决定**：规则写成 `schemas/<文书类型>.json`，代码只做通用校验：

```json
{
  "kind": "监理通知单",
  "fields": ["部位", "事由", "受检单位", "整改要求", "整改期限", "检查结论", "签发人"],
  "placeholders": ["待补", "待定", "待确认", "未知", "不详", "N/A", "/", "-", "无"]
}
```

**理由**：

- 加一种文书类型 = 加一个 json 文件，不用改代码、不用重新测
- 同一条规则同时给「agent 自查」和「落库把关」用，不会两边打架
- 不是"后端替模型判断内容"，只是按声明好的字段清单核对 —— 模型仍然自己决定写什么

**代价**：

- 每个文书类型要维护一份 schema，加类型时容易忘记同步
- 只能判"有没有"，判不了"写得对不对"（后者要靠复核 agent）
- 句子里夹着「待补」不算缺（只认整字段是占位词），这是有意的：
  宁可漏判，也不要让后端去猜语义

**什么情况推翻**：如果字段清单开始频繁变动、或者出现"不同类型的同名字段含义不同"，
就该把 schema 挪进数据库（带版本），而不是继续躺在文件里。

## D14 · 每轮任务改成常驻 app-server，不再起子进程

**背景**：原来每轮任务 `easycode exec` 起一个子进程，启动 + 扫仓库要 5~10 秒，
用户从发消息到看见第一个字要等 8 秒以上。

**决定**：改用 `easycode app-server` 常驻，每个项目一条进程、一个线程，会话复用。

**实测**（同机同模型）：

| 场景 | exec | app-server |
|---|---|---|
简单一轮 | 8~14 秒 | 2.6 / 2.3 秒 |
带工具一轮 | 14 秒+ | 4.8 / 4.1 秒 |

**代价**：

- 进程常驻要盯：挂了要能自愈（已做：`alive()` 检查 + 重建）
- 一个项目一个线程，长期不用的项目会有内存占用（暂不回收，量小）
- 事件名和 exec 不一样（驼峰 + delta），要一层翻译；翻译层是新的出错点
  （这次就栽在"正文在 delta 里、completed 里是空的"）

**什么情况推翻**：如果改成多实例部署、或者需要按用户隔离上下文，
就该把线程池换成"按 用户+项目 分配"，而不是现在的按项目。

## D15 · 引擎的注册表 / 提示词，能问工具就别手写

**背景**：提示里的可用工具清单原来手写在 `agent.py` 里。加了 `validate_doc`
之后，agent 依然不知道有这个工具 —— 因为没人记得改那段字符串。

**决定**：工具清单问 `jl-tool list` 自动生成（`tool_manual()`）；
`allowed_tools()` 也从同一处取。

**代价**：

- 每次渲染提示多一次子进程调用（几十毫秒，可接受）
- 工具描述写得太长会撑爆提示，所以只取第一句

**什么情况推翻**：如果工具多到几十个，就该按任务相关性筛（用 `tool_search`），
而不是全量列出来。

---

## D16 · 复核先用同会话第二轮，不等多 agent

**背景**：出稿质量参差：有的缺字段、有的不写依据、偶尔还有人把「待补」当值写进去。
理想做法是派一个独立的复核 agent，但多 agent 被 `encrypted_content` 卡住。

**决定**：先用同一个会话的第二轮做复核 —— 不新建 agent，
只把「审一遍」交给同一个 agent 的下一轮。等 R4 打通再换成独立 reviewer 角色。

**为什么不是后端校验**：后端只能查「字段有没有」，
查不出「结论有没有依据」「有没有自相矛盾」。那类判断必须由模型做，
所以写成一轮对话，而不是一堆 if。

**代价**：

- 出稿任务耗时翻倍（实测 45 秒 → 89 秒）
- 同一个 agent 审自己，容易顺着自己的思路走，独立性不如独立 reviewer
- 多一条消息，前端要能分开显示（现在是两条 assistant 消息）

**什么情况推翻**：多 agent 打通后立刻换独立 reviewer；
或者用户嫌慢，就改成「只在 state=待补 或高风险类型时复核」。

## D17 · 为了多 agent，自己编引擎（带补丁）而不是换线路

**背景**：多 agent 被 `encrypted_content` 卡住。两条路：换一条完整实现
Responses 的线路，或者自己编带补丁的引擎。学校的中转不能充值，
百炼又不透传加密内容，换线路这条路基本断了。

**决定**：自己编。服务器上本来就有 `jl-easycode-build:local` 构建镜像，
补丁只有三处，编译 11~13 分钟。

**代价**（必须记住）：

- 引擎从此是**我们改过**的版本，升级要重新打补丁、重新编译
- 每次编译前要停 BFF，否则 `cp` 报文件忙；重启后要确认 8081 没被旧进程占
- 二进制 283MB，跟着仓库走不现实，只保留补丁文件

**什么情况推翻**：如果将来用上完整实现 Responses 的官方线路，
就该丢掉补丁回到原生版本；或者上游把 `AgentMessage` 的加密清理补上，
我们自己这条补丁就可以删掉。

## D18 · 改 engine 的模型目录：最小改动，别顺手“优化”

**背景**：要让子 agent 用百炼的模型，得把模型加进 `models-manager/models.json`
（`include_str!` 编进二进制）。

**踩的坑**：第一次加了 5 个模型，并顺手把 websockets / responses_lite / verbosity
这些能力位按“非 OpenAI 应该关掉”的想法置空 —— 结果**整个模型目录变空**，
`model/list` 返回 0 条，连原有的 gpt-* 全没了。子 agent 一个模型都选不了。

**决定**：克隆一条现成的条目，**只改身份字段**：
`slug` / `display_name` / `description` / `context_window` / `max_context_window`。
其它能力位一律不动。

**代价**：

- 新条目会继承模板模型的能力位（比如 code_mode_only），和百炼真实能力不完全一致
- 每加一个模型都要重新编译（11~13 分钟）

**什么情况推翻**：如果将来要按模型精确控制能力（比如真的关掉 verbosity），
就得先把 `ModelInfo` 的校验规则读透、加一个能验证目录有效性的自检脚本，
再动这些字段。

## D19 · 复核改用「独立会话」，不再让主 agent 自己 spawn

**背景**：D16 定的是「同会话第二轮自审」，当时的理由是 spawn_agent 不通。
后来多 agent 打通了，但实测主 agent 调 `spawn_agent` 仍会间歇性返回
`unsupported call`（引擎内部路由问题，不是模型没试）。

**决定**：复核由 BFF 开**一条独立线程**来做：

```python
thread/start { cwd, model: REVIEW_MODEL, developerInstructions: 复核员角色 }
turn/start  { 让它读文书 + validate_doc }
thread/close
```

好处：模型可选（`qwen3.8-flash` 便宜）、上下文干净、跑完就关，
不依赖那个时好时坏的工具。

**代价 / 未解决**：

- 独立线程仍会加载项目 AGENTS.md，reviewer 会被里面的多 agent 说明带偏，
  实测输出变成「spawn_agent 调不通」的元讨论，而不是审查意见（未解决）
- 多一条线程要关，关失败会泄漏；已用 finally + try 兜住

**什么情况推翻**：如果给独立线程做一个只读的干净 cwd（不含 AGENTS.md），
或 `thread/start` 支持完全替换 baseInstructions，就该改成那种更彻底的做法。

## D20 · 复核结果不单独成条消息

**背景**：复核做成独立会话后，BFF 又给它插了一条 assistant 消息。
结果用户在聊天里看到的最后一条是复核的 `FINAL_ANSWER` 信封，
而图文消息本来那句回答被挤到上面去了 —— 看起来就像「AI 没理我的图」。

**决定**：复核结果并进**同一条** assistant 消息：
`answer.review` 存全文，时间线里加一条「复核意见」note。
聊天只多一个可展开的条目，不多一个气泡。

**代价**：

- 复核要多等一会儿才出结果（现在是先复核再入库，总时长略增）
- 前端要读 `answer.review` 才能展示复核；目前只在时间线里能看到

**什么情况推翻**：如果将来希望复核和出稿在界面上是两条独立记录
（比如各自可批注、可签字），就该拆成两条，但要给它们不同的类型标记，
不能都当普通 assistant 消息。

## D21 · 会话按「项目 + 用户」隔离，不按项目

**背景**：常驻 app-server 为了复用上下文，原来只按 project_id 维护客户端。
结果是同一项目里不同用户共享一条线程：B 能看到 A 说过的话。
演示时无所谓，一旦两个监理员同时用一个项目就是串话。

**决定**：客户端键改成 `project#user`；`run_stream` / `run_isolated` 都带 user_id。

**代价**：

- 一个项目 N 个人 = N 条常驻进程，内存随人数线性增长（目前量级无感）
- 同一个人的跨设备对话仍然是同一条会话（这是想要的）

**什么情况推翻**：如果要做「项目共享记忆、个人私有上下文」两层，
就得在会话之上再加一层项目级的共享记忆（不是简单共享线程）。

## D22 · 图片要标明「本轮」和「历史」

**背景**：会话复用意味着历史里也有图片。用户发新照片时，模型把历史图片
也当成这一轮的来复述，看起来就像「理解错了」。

**决定**：带图时在提示里写清「本轮附件 N 张，只针对这几张回答，
历史图片不要重复描述」。

**代价**：提示变长一点点；模型仍可能偶尔越界，但实测两轮不同颜色的图不再串。

**什么情况推翻**：如果能给每条消息带上独立的附件清单（结构化而不是靠提示），
就不需要这段提示了 —— 那需要引擎支持 per-message attachments。

## D23 · 只保留一条线路，旧中转从代码里删掉

**背景**：换到百炼时代码只改了引擎那一层，`llm()`（学习/记忆抽取）
还指着旧中转。结果学习一直 403，谁也没发现 —— 因为失败是静默的。

**决定**：删掉旧中转的全部引用（provider 段、`.env` 的 key、注入逻辑），
让代码里**只有一条线路**。留一段注释说明历史原因即可。

**为什么不是“保留作备用”**：留着就等于留了一个会静默失败的岔路。
真需要备用，应该是显式切换（改 `LLM_BASE`），不是代码里两个默认值。

**代价**：旧中转真要用时得改 `.env`（`LLM_BASE` + `LLM_KEY`），不是改代码。

**教训**：**切换外部依赖后，要 grep 全仓残留**。
这次是靠用户问“为什么不学习”才发现的。

## D24 · 记忆不自研：每个用户一个 EASYCODE_HOME

**背景**：原本打算自研一套记忆（MySQL 表 + 字面相似度去重，后来还想上向量）。
查源码发现两件事：

```
core/src/config/mod.rs:992  EASYCODE_HOME 可覆盖家目录
memories/read/src/lib.rs:13 memory_root = $EASYCODE_HOME/memories
```

**决定**：不自研。每个用户启动 app-server 时给一个 `EASYCODE_HOME`：

```
data/homes/<user>/  →  memories/ sessions/ skills/ config.toml
```

记忆、会话、技能天然按用户隔离；项目边界靠引擎整理提示词强制的
`applies_to: cwd=...` 字段。MySQL 的 memory 表保留为历史归档，不再作主存储。

**为什么不是自己写**：引擎的整理提示词 880 行，涵盖去重、冲突、边界、脱敏。
自己写只会更差，而且错在哪都看不出来。

**代价**：

- 每个用户一个常驻进程 + 一份家目录（内存/磁盘随人数增长）
- 引擎记忆在**会话启动时**跑（`start_memories_startup_task`），不是每轮
- 需要显式确认 `[features] memory_tool` 是否开启

**什么情况推翻**：要做「项目共享记忆、个人私有偏好」两层时，
引擎的单人记忆模型就不够用了，得在外面再叠一层项目级共享。

## D25 · AGENTS.md 只写事实，行为交给 skills

**背景**：现在的 AGENTS.md 有 2778 字节，混了项目事实、项目规矩、
工具清单、说话方式。加一个工具就得改这段字符串（我们真忘过）。

**决定**：AGENTS.md 只允许三类内容 —— 项目事实、项目约定、指针。
工具用法和输出风格移进 `data/knowledge/skills/`，按需读。

判断标准：**这句话会不会因为加工具/换模型而失效？会 → 不许写。**

**代价**：agent 要学会主动读 skill；短期内可能偶尔不读就动手（观察再调）。

**什么情况推翻**：如果去掉行为提示后，任务质量明显下降，
就说明有些行为约束确实是必要的 —— 但要改成 skill，而不是塞回 AGENTS.md。

## D26 · BFF 绑 0.0.0.0，工具容器统一用 host-gateway 访问

**背景**：MCP 工具容器在 jl-net 桥接网络，BFF 只绑 127.0.0.1，
于是容器里的 `create_doc_draft` 永远 `fetch failed` —— 文书文件写了、库没进，
agent 还会手写文件并声称完成。这个 bug 藏了很久，因为 exec 路径用 host 网络能通。

**决定**：BFF 监听 0.0.0.0（可用 `BIND_HOST` 收回）；MCP 容器用
`--add-host host.docker.internal:host-gateway` + `BFF_URL=http://host.docker.internal:8081`。

**代价**：8081 在局域网可达。服务器无公网入口，公网访问走反向代理；
以后加鉴权时要把这个口子一起收。

**什么情况推翻**：如果 BFF 要做多机部署，就不该用 host-gateway，
应该让 BFF 也进 jl-net、用容器名互相访问。

## D27 · 契约行保留在 AGENTS.md，只搬走工具手册

**背景**：瘦身时把「必须用 create_doc_draft」也删了，结果 agent 改用 shell 手写文件，
doc 表没有记录（实测 3 份孤儿文件）。

**决定**：AGENTS.md 保留一行**领域契约**（出稿必须走工具、手写不算），
但工具清单、参数、说话风格全部移进 skills。
判据不是「是不是行为」，而是「**删了它会不会绕开工具的副作用**」。

**代价**：这一行会随工具名变化而失效（改名时要改）。

**什么情况推翻**：有了 PostToolUse 钩子能强制拦截「写了 md 但没入库」时，
这行就可以删 —— 让机制兜底，而不是靠提醒。


## D28 · MySQL 记忆的去重仍用字面相似度（技术债，待清）

**现状**：`learn_from_turn` 写 MySQL `memory` 表前，用 `similar()`（bigram 相似度 >0.8）
判断是否重复。同一句话换两种说法（「整改回复必须附对比图」/「整改要配前后对比照片」）
**判不出来**，会存两条。

**为什么这是债**：用户明确否掉了「记忆去重靠字面相似度」这个方向 ——
文件 + 模型整理才是对的做法，而且引擎记忆那套已验证能合并同义句。

**为什么先留着**：MySQL 记忆目前还承担「当场生效」（渲染进 AGENTS.md 的【项目规矩】），
引擎记忆要等会话闲置 ≥1 小时才抽取，中间有空窗。

**清债方案**（等拍板，见 `docs/DESIGN-记忆单一来源.md` 选项 C）：
写之前让模型判断「这条是不是新的」，而不是算字符串相似度；每轮多一次小调用（1~3 秒）。

**还债条件**：D28 被解决时，删掉 `similar()` 在 memory 写入路径上的调用。


## D29 · 开鉴权前必须补的 13 个写接口权限校验（阻塞项）

**怎么发现的**：`scripts/audit-auth.py` 静态比对「路由 → 处理函数 → 是否调用 guard_project」。

**现状**：`member_of()` / `guard_project()` 存在且被 20 处调用，
但下列**写接口没有项目级校验**（`AUTH_REQUIRED=0` 时全部放行，所以现在看不出问题）：

```
POST   /api/v1/docs                      handle_doc_create       建文书
POST   /api/v1/docs/validate             handle_doc_validate     校验文书
POST   /api/v1/memories                  handle_memory_create    写记忆
PATCH  /api/v1/memories/(\d+)            handle_memory_patch     改记忆
DELETE /api/v1/memories/(\d+)            handle_memory_delete    删记忆
POST   /api/v1/projects/([\w-]+)/render-memory  handle_render_memory
POST   /api/v1/tasks/(\d+)/retry         handle_task_retry       重试任务
POST   /api/v1/project                   handle_project_save     存项目
DELETE /api/v1/project                   handle_project_save     删项目
POST   /api/v1/asr                       handle_asr              语音转写
POST   /api/v1/standard                  handle_standard         写规范
POST   /api/v1/projects                  handle_project_create   建项目（可放行：创建者即成员）
POST   /api/v1/auth/logout               handle_logout           （可放行：只影响自己）
```

**为什么没现在改**：
1. 这是安全策略变更，且 `AUTH_REQUIRED` 一开会影响小程序（需要先接微信登录）；
2. 有些接口要区分「项目成员」和「平台管理员」，这是产品规则，得你定。

**开鉴权的前置条件**：上面 13 个里除「建项目 / 退出登录」两个可放行外，
其余 11 个必须加 `guard_project(project_id, user)`，并补一条回归用例
（A 项目的人不能改 B 项目的文书）。

**顺带记**：审这个的第一版脚本用「全局扫 handler 名再和路由 zip」对齐，
结果只匹配到 1 条就宣称「全部做了校验」——**假阴性**。
重写成「从路由行往后找处理函数」才拿到真数据。教训：审计脚本自己也要验证。

# D30 · 记忆单一来源：文件是知识，数据库是索引

**决定**：三类知识只有文件是权威来源；MySQL `memory` 表降级为索引（谁在什么时候说过这条）。

```
组织知识   data/knowledge/**           只读，git
项目规矩   <ws>/records/rules.md       人写，git
项目证据   <ws>/records/photos.md      看图后追加一句描述，git
项目流程   <ws>/.easycode/skills/**    Repo scope，引擎自动列目录
个人知识   $EASYCODE_HOME/memories/**  引擎整理；人只能追加 notes/
```

**推翻条件**：如果需要跨项目检索个人记忆（"我以前在哪个项目见过这种问题"），
再考虑给文件加索引；不许先上向量库。

# D31 · preflight 增加「真 import」检查

**为什么**：删函数忘改 import 这类错误，语法检查和「未定义调用」检查都抓不到，
但会让服务完全起不来（今天发生过一次）。

**做法**：`python3 -c "import bffpkg.api"`；本机没装 pymysql 时插桩模块；
不在服务器上时跳过（`core.ROOT` 是服务器路径，本机 import 必然失败）。

**代价**：这条检查只在服务器上真正生效 —— devloop 每天 09:00 会跑它。
