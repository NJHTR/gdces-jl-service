# 设计稿：记忆的单一来源（需要你拍板，我不动手）

> 按 LOOP-PROMPT「【D 结构要变】只写设计稿，停下等人」写的。
> 发现的是一个结构性重复，不是 bug 修一下就好。

---

## 一、证据（06:50 实测）

`data/workspaces/test-sandbox/AGENTS.md` 里注入的「项目规矩」：

```
- 整改回复必须附整改前后对比照片
- 整改必须配前后对比照片                    ← 同一条，两种说法
- 规范库查不到相关条文时，依据栏留空，不硬编
- 监理文件依据栏：规范库查不到条文时留空，严禁硬编   ← 同一条，两种说法
```

这些来自 MySQL `memory` 表。而引擎记忆（`homes/<user>/memories/MEMORY.md`）
整理时**会把同样的说法合并成一条** —— 我们实测过（三种说法 → 一条）。

所以现在是：

```
同一条规矩，两套存储，两套去重能力
MySQL：来一条存一条（我现在每次 learn_from_turn 都插入）
引擎：模型读取→合并→重写（能去重）
```

## 二、为什么会变成这样

D24 决定「记忆不自研，用引擎的」，但当时的落地只做了「每用户一个
EASYCODE_HOME」，**没有停掉旧的 MySQL 学习路径**。于是两个写者都在写：

```
learn_from_turn  → MySQL memory 表 → 渲染进 AGENTS.md【项目规矩】
引擎记忆管线      → MEMORY.md → 引擎自动注入 memory_summary
```

这正是 R6「一张表一个写者」被违反的样子，只不过它们不是同一张表，
而是**同一个概念有两个来源**。

## 三、三个选项

### 选项 A：MySQL 记忆只读归档，写入全停

```
learn_from_turn 不再 INSERT MySQL
AGENTS.md 的【项目规矩】不再从 MySQL 渲染
记忆完全由引擎负责
```

- ✅ 彻底单一来源，去重交给模型（已验证有效）
- ❌ **空窗期**：引擎要等「会话闲置 ≥1 小时」才抽取，新规矩 1 小时内不生效
- ❌ 现在只有用户 501 有引擎记忆；其他 20 个用户会突然「没有规矩」

### 选项 B：保留 MySQL 作为「即时记忆」，引擎作为「长期记忆」

```
MySQL：当场记住（即时生效，渲染进 AGENTS.md）
引擎：慢慢整理（跨会话、跨项目边界）
两者分工，接受短期重复
```

- ✅ 新规矩立刻生效（监理员当场说的，下一秒就带上）
- ✅ 改动最小
- ❌ 重复还在，只是被解释成「分工」
- ❌ 长期会积累措辞不同的一堆

### 选项 C：MySQL 写入时做一次「让模型判断是不是新的」

```
learn_from_turn 里，先拿这条规矩和已有列表比对：
  新 → 插入；重复 → 跳过/替换
比对由模型做（一次小调用），不是字面相似度
```

- ✅ 即时生效 + 不重复
- ✅ 符合「去重靠模型，不靠字符串」
- ❌ 每轮多一次 LLM 调用（约 1~3 秒、几分钱）
- ❌ 又多了一个「谁来决定」的地方（虽然决定者是模型）

## 四、我的建议

**选项 C，但只在真有必要时触发**：

```
用户说了「记住 / 以后 / 规矩 / 必须」这类明确的规矩 → 走一次模型比对
普通对话 → 不写记忆（反正引擎那边会慢慢整理）
```

理由：监理员在工地说的规矩，必须**马上**生效（等不了 1 小时）；
但又不该存成一堆同义句。

## 五、要你回答的三个问题

1. **新规矩要不要「立刻生效」？**
   要 → 只能选 B 或 C；不要 → 选 A（简单，但会慢 1 小时）

2. **能不能接受每轮多一次小模型调用（约 1~3 秒）？**
   能 → 选 C；不能 → 选 B

3. **现有那 21 条 MySQL 记忆要不要清一遍？**
   里面至少有 4 条是同义重复（上面证据里那两对）。

## 六、我不动手的原因

这动的是「记忆从哪来」这件事，属于 GOAL 级别的结构；
而且选错会让「当场说的规矩」失效 —— 比现在重复更糟。
