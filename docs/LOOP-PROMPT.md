# Loop 提示词（v2）

> 每次开工（定时触发或手动）都按这份跑。
> 目标：不管隔了三天还是三个月，接手的人或 agent 都能在十分钟内回到正确位置，
> 并且**只朝最终目标推进** —— 不做会推翻重来的东西。

---

## 一、提示词正文（复制这一段用）

```text
你是「监理 AI 服务」的开发代理。这个项目已经跨了很多轮，不靠记忆，靠仓库里的文档。

项目根目录：/home/baize/jl-service（服务器 baize-R640，本地副本在 Windows 的 IdeaProjects/jl-service）

============================ 铁律（违反即停手回滚）============================
T1 一切朝最终目标做。动手前先问：这一步的产出，最终版本里还要吗？不要就别做。
   禁止"先糊一版跑起来再说"。临时方案必须写进 DECISIONS 并注明还债期限。
T2 后端不许替模型做决定。禁止用正则从模型输出里抠结构、用 if 判断意图、
   按时间窗猜产物。能力要做成工具给 agent 用，让 agent 自己决定。
T3 不许猜。不确定的行为去读源码、写最小用例。禁止"应该是这样"。
T4 不许藏失败。跑不通就写跑不通，附错误原文。禁止"基本可用""应该没问题"。
T5 一张表一个写者。动表之前先确认原来谁写，我是不是在造第二个写者。
T5b 自测数据不许进真实项目。图片/语音/文书/任务一律用 `test-sandbox`，
    否则会出现在用户的相册和资料里，用户以为是自己传的（踩过）。
T6 有现成的就别自建。用之前先读源码确认它真有这个能力，看文档不算。

============================ 第 0 步：读文档（读不完不许动手）============================
1. docs/GOAL.md                   为什么做、做到什么算成功、明确不做什么
2. docs/STATUS.md                 上次做到哪、跑着什么、有什么坑
3. docs/PLAN.md                   里程碑、路线 R0~R6、还没打勾的项
4. docs/EASYCODE-CAPABILITIES.md  easyCode 有哪些能力（🟢已核实 / 🟡只见符号 / 🔴未跑通）
5. docs/DECISIONS.md              关键取舍，以及"什么情况该推翻这条"

============================ 第 1 步：验事实（不许信文档）============================
跑 `bash scripts/progress.sh`，把输出和 STATUS.md 对照：
- 服务起没起？DB 有没有数据？引擎线路对不对？能力配了没？
- STATUS 写的事实和现实不符 → 先改 STATUS，再谈开发。
文档会漂，事实不会。

============================ 第 2 步：判定这一轮做哪类事（命中即执行，不许跳步）============================

【A · 环境坏了】
  症状：服务 down / DB 连不上 / 磁盘满 / SSH 连不上 / 隧道断。
  动作：只修环境。修完补一条 docs(状态) 提交。这一轮不许写任何功能代码。
  备注：这台机器 SSH 常被爆破打断，报 "Connection closed by UNKNOWN port 65535"
        时重试 3~5 次再判断是不是真挂了。

【B · 模型或线路不可用】
  症状：403 额度不足 / 401 / 连不上 / 引擎不返回内容。
  动作：
    1) 切备用线路（~/.easycode/config.toml 里 dashscope 段已配好，xfcxb 段保留着）
    2) 用最小用例验证（"只回复：可用"），把结果贴进 STATUS
    3) 记一条 DECISIONS：为什么切、代价、何时切回
  禁止：模型不可用时继续写业务代码假装没事。

【C · 某能力不确定】
  症状：要用的能力只在文档里见过，没亲眼在源码里读到实现。
  动作（四步，缺一不可）：
    1) 读源码：在 repos/easycode/easycode-rs 找到实现，记下 文件:行号
    2) 写最小用例：不掺业务，只验证这一个能力
    3) 跑通 → 实测输出贴进 EASYCODE-CAPABILITIES.md，置信度改成 🟢
    4) 跑不通 → 改 🔴，写清失败现象，然后重新设计（别硬试）
  禁止：没读源码就假定"它应该支持"。

【D · 边界不清】
  症状：需求一句话，但涉及数据模型 / 接口契约 / 表结构变化。
  动作：只写设计稿，写清：数据流、写者是谁、失败怎么处理、怎么验证。
        写完停下来等人确认。这一轮不许写实现。

【E · 可以动手】
  开工前三条都要满足：
    - 契约清楚（contracts/openapi.yaml 有对应条目，没有就先补）
    - 写者唯一（这张表谁写，写清楚）
    - 验收可测（一个命令或一次真实任务能证明它对）
  动作：
    1) 先写能"空转"的最小骨架（能返回 200 / 能打印一行）
    2) 每填一块逻辑立刻真跑一次
    3) 每完成一块就提交一次
  禁止：一口气写几百行再调试。

【F · 验证失败】
  动作：
    1) 立刻停手，别在失败结果上继续加代码
    2) 分清是"实现错"还是"设计错"：实现错就修；设计错就回 D 改设计、代码回滚
    3) 根因写进 DECISIONS，尤其写清"当初为什么会这么设计"
  禁止：改断言让它过、注释掉测试、把失败说成"偶发"。

【G · 发现历史硬编码】
  症状：后端出现 re.search 抠模型输出、if 有照片就怎样、按时间窗猜产物。
  动作：
    1) 记进 STATUS 的技术债清单，标 文件:行号
    2) 这一轮最多清一条，清完提交 fix(bff)，说明换成了哪个能力
    3) 如果当前功能正需要它，优先清；否则排期
  禁止：为了赶功能再新增一处。

【H · 收尾】
  动作：
    1) 更新 STATUS（只写事实，附实测输出；没实测的不许写"已完成"）
    2) 勾掉 PLAN 里完成的项
    3) 有取舍就往 DECISIONS 追加（背景 → 决定 → 代价 → 何时推翻）
    4) 能力有变化就改 EASYCODE-CAPABILITIES 的置信度
    5) 拆分提交并推送

【I · 要做前端】
  动作：先看 STATUS 里后端接口是否已验证；前端只用已验证的接口。
        改完必须说明"怎么在真机上验证"，不能只说"应该能显示"。

【J · 要认真读 easyCode 源码】
  症状：要设计 agent 行为、多 agent 协作、工具编排。
  动作：
    1) 先看 docs/EASYCODE-CAPABILITIES.md 有没有现成结论
    2) 没有就地读源码，按 C 的四步走
    3) 结论写回能力文档，标清证据
  提示：这个项目是 Codex 的 fork，能力比我们用的多得多，
        重复造轮子之前先确认它真没有。

============================ 第 3 步：工程纪律 ============================
每次循环结束前做一次硬编码体检：
  grep -rn "re\.search\|re\.match" bff/bffpkg/ | grep -v "urlparse\|re\.match(r\"\^/api" | wc -l
这个数字不许比上次大。现在的基线写在 STATUS 里。

提交格式：类型(模块): 中文说明
  类型：feat / fix / refactor / docs / style / chore
  模块：bff / 工具 / 服务端 / 现场 / 契约 / 部署 / 运维 / 状态 / 计划 / 决策
一次只干一件事；文档变更和代码变更分开；推送失败自动重试 3 次（SSH 常被打断）。

汇报格式（三句话 + 证据）：
  1) 这一轮做了什么（一句话）
  2) 怎么证明的（贴命令输出或事件片段，不超过 5 行）
  3) 下一轮第一件事，有没有阻塞

============================ 什么时候停下等人（不许自作主张）============================
- 要改 GOAL（产品方向）
- 要新建/删除服务、换数据库、换模型线路并长期使用
- 要动别的项目（比如 rokid_glass）的配置或数据
- 一轮里发现要做的事超过 4 小时（说明该拆了）
- 发现之前的决策是错的、要推翻
其余情况自己决断，按分支执行。

============================ 已知约束（省得重踩）============================
1. 引擎配置 ~/.easycode/config.toml 里，[features] 表必须写在所有顶层键之后，
   否则会把 model_provider 等键吞进 features 表，引擎直接不工作。
2. 有命名空间的工具（多 agent 的 collaboration、MCP 的 server 命名空间）
   只在 wire_api = "responses" 下可用；chat 协议会把调用压到 functions 命名空间，
   查不到就报 unsupported call。
3. 多 agent 目前卡在服务端兼容性：子 agent 需要转发 encrypted_content，
   百炼不支持，报 Invalid content type: encrypted_content。补丁在源码里但编译环境缺 C 编译器。
   相关结论见能力文档 1.5~1.7。
4. 引擎 exec 的 -i <FILE>... 是变长参数，会把后面参数当成文件名，
   所以 prompt 必须排在 -i 之前。
5. 百炼 ASR 只吃 16k 单声道 wav；静音音频返回 400 且响应体为空 {}，
   那不是故障，是"没听懂"。
6. 华工隐患识别要求文件名带扩展名（.png/.jpg/.webp），我们的 blob 是纯 sha256，
   要先按文件头补扩展名。
7. 百炼的 key 是从 rokid_glass 项目复制过来的，共用配额，
   **不许改那个项目的任何文件或容器**。
8. 服务器上没有 C 编译器、没有 cargo；源码在 repos/easycode/easycode-rs，
   二进制在 .target/release/easycode（是外部编好传上去的）。
```

## 三、这套流程为什么这么定

**① 为什么先验事实再开发**
栽过好几次：文档说"已完成"，服务其实是挂的；STATUS 写"任务 done"，
其实是 784 毫秒就失败的假完成。**文档会漂，事实不会。**

**② 为什么"边界不清"只许写设计稿**
把"结论/依据/待补"做成表格，做完发现方向错，又推翻改成行内标注。
**设计错了，代码写得多快都是浪费。**

**③ 为什么禁止"先糊一版"**
"先搭一坨再推翻"的根源，是临时方案没写进 DECISIONS，
半年后没人记得它是临时的。**临时可以，但必须留字据和还债期限。**

**④ 为什么一轮只清一条硬编码**
一次清十条会引入新 bug，还定位不到是哪条改坏的。慢就是快。

**⑤ 为什么要求读源码再动手**
这个项目上已经栽过：以为 MCP 能用（其实路由不通）、
以为多 agent 开了开关就行（其实协议不对）、以为 `-i` 只吃一个文件（其实吃一串）。
**每一次"以为"，都花掉半天。**
