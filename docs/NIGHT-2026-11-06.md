## 二、找到并修掉的真问题

1. **文书静默不入库**（最严重）
   BFF 只监听 127.0.0.1，MCP 工具容器在桥接网络里 → `fetch failed` →
   agent 手写文件并宣称成功，用户在系统里看不到。已修（绑 0.0.0.0 + host-gateway）。

2. **上传的图永远进第一个项目**
   小程序把 `projectId` 放在 formData，后端只读 query。已修。

3. **`jl-tool` 没进 PATH**（带图慢的真凶之一）
   模型在文件系统里找工具，白花 8 次调用、二十几秒。加软链接后 80s → 24s。

4. **复核员找错目录**
   去 `docs/` 找，文件在 `docs/2026-11-05/`，于是它说"文书不存在"。
   现在直接把绝对路径给它，复核意见变得具体（"受检单位待补，无法送达，文书不成立"）。

5. **瘦身时删掉了"缺项留空、不要追问"**
   它开始连问五个问题而不出稿，违反零必填。已补回。

## 附：preflight 三条硬线

```
1. 调用了不存在的东西（Python 名字 / JS 私有方法）
2. 静默失败数（except+pass）只能降不能升，基线 13
3. 硬编码数（re.search/re.match）只能降不能升，基线 11
```

## 附：08:35 追加 —— 三类并发问题（这一段比前面所有都重要）

**单个用户测试永远测不出来，上线给两个监理员同时用就会撞。**

### 1. 串单：出稿结果写在项目级共享文件

```
.agent/last.md  →  两个人同项目同时用，后启动的删掉先跑的产物
                   实测：221 的复核意见出现在 223 的回答里
修：.agent/last-<task_id>.md
验证：同项目两个用户并发，各拿各的结果，0 次归属不符
```

### 2. 语音转写串号：临时文件全局共用

```
/tmp/jl-asr.wav  →  两人同时发语音，其中一人拿到别人的转写
修：/tmp/jl-asr-<随机>.wav
```

### 3. 复核互踩：工作目录全局共用

```
/tmp/jl-review  →  所有复核共用一个目录
修：/tmp/jl-review-<task_id>
```

### 代价与补救

隔离之后临时产物会堆积，所以加了 `cleanup_temp`（每天 04:00，
只删超过 1 天的）—— 这条也挂在服务侧的 service_job 上。
