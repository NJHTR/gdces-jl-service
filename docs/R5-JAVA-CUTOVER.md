# R5 调研：Java 业务替换（结论：现在不做）

> 只读调研，未改任何代码。结论先行：**不建议现在切**，理由不是"麻烦"，
> 是切过去会造成第二个写者。

---

## 一、现状（实测）

```
service-java/                 Spring Boot + MyBatis
进程                          java -jar service-java/target/jl-biz-0.1.0.jar（pid 2353522）
端口                          8082（监听 *:8082）
接口                          /api/v1/docs（list / detail / register / patch）
数据库                        同一个 MySQL（127.0.0.1:3309/jl）
```

**关键事实：BFF 完全没有调用它。** 全仓搜索 `BIZ_BASE_URL` / `8082`：

```
bff/bffpkg/*.py 里 0 处引用
```

也就是说：**Java 服务在跑，但没有任何流量进来。**

## 二、为什么不能直接切

### 1. 它会是 `doc` 表的第二个写者（违反 R6）

现在 `doc` 表的写者有且只有两个：

```
tools/src/tools.js create_doc_draft  → 写文件 + git 提交
                                     → POST /api/v1/docs/register（BFF）→ 写库
bff/bffpkg/agent.py                  → patch/状态流转
```

Java 的 `DocController` 也有 `register` 和 `patch`，**同样直连那个库**。
一旦切过去，或者两个都在跑且有流量，就可能出现：

```
同一份文书两行记录 / 状态被两边来回改 / 审计对不上
```

### 2. 切换要动的地方比看起来多

```
/api/v1/docs/register    工具侧在调，改了要同步改 tools（还在容器镜像里）
/api/v1/docs           小程序列表在用
/api/v1/docs/{id}      文书详情页在用
/api/v1/docs/{id} patch 补字段在用（这是最热的写路径）
```

这四处**全部在 BFF 里已经跑通并被实测验证**，切过去等于把验证过的换成没验证过的。

### 3. 好处不明确

Java 这边目前只有 docs 一族接口，**没有**：

```
出稿编排（agent 会话、复核、异步）
多模态（图片/语音）
知识包同步（standard 表）
定时任务（service_job）
审计、权限、统计
```

切过去只能切 docs 那一层，剩下的还是 Python。**两套语言维护同一套业务，成本上升。**

## 三、建议（按优先级）

1. **短期：把 Java 服务停掉或改成只读**
   它在跑但不接流量，是"随时可能被误连"的风险点。
   （停服务属于部署变更，需要你点头。）

2. **中期：如果确实要用 Java，先把 `doc` 表的写者收敛到一处**
   比如 Java 只做查询（只读副本），写仍然走 BFF；
   或者反过来，把 register/patch 全部搬到 Java 并**下线** BFF 的对应实现。

3. **不建议**：两个都在跑、按流量比例切换（灰度）——
   这张表没有冲突检测，灰度会直接产生脏数据。

## 四、什么时候该推翻这个结论

- 团队里没人能维护 Python（人力问题优先于技术问题）
- BFF 的 docs 接口成为瓶颈（目前 40 秒出稿，瓶颈在模型不在 IO）
- 需要 Java 生态的东西（比如接公司统一权限/审计 SDK）

在那之前，**保持现状比切换更安全。**
